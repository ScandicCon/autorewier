## Часть 1. Что за проект

**AutoRewier** (на лендинге — бренд **«ПОДКАПОТ»**) — это сервис для проверки б/у автомобиля перед покупкой или перепродажей. Рынок — Россия.

Как это работает для пользователя:

1. Он даёт ссылку на объявление (Avito / Auto.ru / Drom), VIN и описывает замеченные дефекты.
2. Сервис автоматически вытаскивает данные авто из объявления, оценивает риски, считает стоимость ремонта и запчастей, проверяет VIN.
3. На выходе — вердикт: «стоит смотреть» / «с осторожностью» / «не стоит», чеклист осмотра и PDF-отчёт.
4. Есть отдельный режим перекупщика (экономика перепродажи) и мониторинг объявления (отслеживание изменения цены).

Два входа для пользователя поверх одной логики: **веб-кабинет** (сайт) и **Telegram-бот**. Деньги — подписка **Pro** через **ЮKassa**.

**Технологии:** бэкенд на Python (FastAPI), база PostgreSQL, фронтенд на Vue 3, бот на aiogram, парсинг через Playwright + Chromium, искусственный интеллект через OpenRouter (модель GPT-4o-mini), проверка VIN через Autocode, оплата через ЮKassa, почта через Resend.

**Где сейчас живёт:** фронтенд на **Vercel**, бэкенд на **Railway**.

## Часть 4. Как устроены ключевые подсистемы (простым языком + код)

Общий принцип всего проекта: **функции включаются флагами или наличием ключей, а если ключей нет — система не падает, а мягко деградирует** (демо-режим, синхронное выполнение, ручной ввод). Этот приём повторяется везде.

### 4.1. Парсеры Avito / Drom / Auto.ru (Playwright + Chromium + капча)

Архитектура двухслойная: отдельно **загрузка HTML страницы**, отдельно **разбор полей из этого HTML**. Это важно: загрузка — сложная (антибот), разбор — простой.

**Загрузка** (`app/services/parsers/avito_fetch.py`) — самое тяжёлое место. Avito активно защищается от роботов, поэтому здесь набор приёмов:

- **Playwright работает в отдельном потоке.** Синхронный Playwright нельзя вызывать прямо из асинхронного кода, поэтому браузер крутится в отдельном «рабочем» потоке (`ThreadPoolExecutor`), а основной код ждёт результат. Браузер один на всё приложение и защищён замком, чтобы не было гонок.

- **Маскировка под живого человека:** настоящий User-Agent, русская локаль, московский часовой пояс, нормальный размер окна, плюс скрипт, который прячет «флаг автоматизации» браузера:
  ```python
  context.add_init_script(
      "Object.defineProperty(navigator,'webdriver',{get:()=>undefined});")
  ```

- **Два режима браузера:** «новый Chromium на каждый запрос» (стабильнее) и «постоянный профиль на диске» (хранит куки Avito, чтобы не проходить капчу повторно).

- **Определение блокировки:** сервис ищет в начале страницы маркеры капчи и блокировки (`captcha`, `подтвердите`, `firewall`, коды ошибок 403/429) и понимает, что его заблокировали.

- **Стратегия отступления:** сначала Playwright, если не вышло — обычный HTTP; при капче — повтор через постоянный профиль; запасной адрес мобильной версии `m.avito.ru` (она легче); кэш страниц; повторы с паузами и общий лимит времени на запрос (90 секунд), чтобы запрос не висел вечно.

- **Поддержка прокси** (включая провайдерский формат `host:port@user:pass`) с понятной диагностикой ошибок.

- **Понятный результат:** функция возвращает не просто «ошибка», а структуру со статусом и подсказкой пользователю — «пройдите капчу», «введите данные вручную», «проверьте прокси».

**Разбор** (`base.py`, `drom.py`) — здесь браузер уже не нужен, работает библиотека BeautifulSoup. Данные берутся из трёх источников по надёжности:

1. CSS-селекторы по спец-атрибутам площадки (`data-marker` у Avito, `data-ftid` у Drom);
2. блок `<script type="application/ld+json">` (стандарт Schema.org — стабильнее, чем вёрстка);
3. сырые JSON внутри страницы (`__preloadedState__`) через регулярки.

Плюс починка «кракозябр» (битая кириллица) и флаг `parse_ok` — если ключевые поля так и не удалось вытащить, пользователю предлагают ввести данные вручную.

Важно: **Drom и Auto.ru проще и статичнее**, поэтому грузятся обычным HTTP без браузера. **Avito требует Playwright** из-за защиты.

### 4.2. Ограничение частоты запросов (Rate limiting)

Файл `app/security/rate_limit.py`. Защита от перебора паролей и спама. Алгоритм — «скользящее окно»: на каждый ключ (например, `login:IP-адрес`) хранится список времён последних запросов. Старые отметки выбрасываются, и если за окно (например, 60 секунд) запросов больше лимита — выдаётся ошибка 429 «слишком много запросов».

```python
while bucket and bucket[0] <= now - window:  # выкинуть старые отметки
    bucket.popleft()
if len(bucket) >= limit:
    return False                              # лимит исчерпан
bucket.append(now)
```

Лимиты у каждого действия свои (вход, регистрация, оплата, вебхук, VIN). Сейчас счётчик хранится **в памяти процесса** — это работает для одного сервера, но сломается, если запустить несколько копий приложения (тогда нужен Redis — об этом в части про масштабирование).

### 4.3. JSON-логи

Файл `app/observability.py`. Обычные логи — это просто строки, их тяжело искать. Здесь сделан свой «форматтер», который превращает каждую запись лога в JSON со стандартными полями: время, уровень, сообщение, и контекст — ID запроса, метод, маршрут, код ответа, длительность. Такие логи легко фильтровать и анализировать в продакшене.

### 4.4. Метрики Prometheus

Тот же файл. Prometheus — стандарт для сбора метрик. Здесь заведены два счётчика:

```python
REQUEST_COUNT    = Counter(...)    # сколько было запросов
REQUEST_DURATION = Histogram(...)  # сколько они длились
```

Специальная «прослойка» (middleware) оборачивает каждый HTTP-запрос: засекает время, по завершении увеличивает счётчики с метками (метод, маршрут, код ответа). Важная деталь — в метку идёт **шаблон маршрута** (`/inspections/{id}`), а не конкретный адрес, иначе меток было бы бесконечно много. Эндпоинт `/metrics` отдаёт всё это Prometheus'у, поверх можно построить дашборды в Grafana.

### 4.5. Админ-API

Файл `app/api/admin_routes.py`. Закрытые служебные эндпоинты, защищённые секретным заголовком `X-Admin-Token`:

```python
if x_admin_token != settings.admin_api_token:
    raise HTTPException(status_code=403, detail="Forbidden")
```

Что отдают: `/admin/health` (живость — пинг базы запросом `SELECT 1`, глубина очереди, версия), `/admin/stats` (счётчики пользователей, проверок, оплат), `/admin/support-status` (какие интеграции включены). Есть и публичные лёгкие пинги `/support/health` для фронтенда.

### 4.6. Redis-воркер для фоновых задач

Файлы `app/services/task_queue.py` и `app/workers/worker.py`. Тяжёлые операции (парсинг, проверка VIN) нельзя делать прямо в момент запроса — пользователь будет ждать. Поэтому сделана очередь на Redis:

- **Кладём задачу:** приложение добавляет задачу в список Redis (`LPUSH`) и заводит запись о её статусе. Пользователю сразу возвращается `task_id`, по которому фронт спрашивает «готово ли?».
- **Воркер берёт задачу:** отдельный процесс в бесконечном цикле забирает задачи из очереди (`BRPOP`), выполняет (например, проверку VIN), и обновляет статус: `в очереди → выполняется → готово / ошибка`.
- **Планировщик мониторинга:** второй бесконечный цикл раз в час запускает проверку отслеживаемых объявлений.

```python
while True:
    item = await client.brpop(queue_name, timeout=5)  # ждём задачу
    ...                                                # выполняем
    await set_task_status(task_id, "succeeded", result=...)
```

Всё включается флагами `TASK_QUEUE_ENABLED` + `REDIS_URL`. Если их нет — операция просто выполняется синхронно (мягкая деградация).

### 4.7. Проверка VIN через Autocode (с демо-режимом)

Файл `app/services/autocode.py`. Интеграция с B2B-API сервиса Автокод. Поскольку отчёт у них готовится не мгновенно, сделана схема «заказать и опрашивать»:

1. `POST .../_make` — заказываем отчёт по VIN, получаем его идентификатор;
2. до 20 раз с паузой 2 секунды опрашиваем, готов ли отчёт;
3. когда готов — вытаскиваем короткую сводку (марка, год, владельцы, ограничения).

**Демо-режим** — ключевой приём. Если ключи Autocode не заданы, вместо реального запроса возвращается заглушка той же формы с пометкой «демо»:

```python
if not settings.autocode_enabled:           # нет ключей Autocode
    if settings.can_use_mock_services:
        return _mock_vin_report(vin)         # отдаём демо-данные
    raise RuntimeError("Autocode is not configured")
```

Благодаря этому весь остальной код (интерфейс, PDF) работает одинаково и с реальными, и с демо-данными — отличается только содержимое.

## Часть 5. Готовность к нагрузке 1000 человек

Допущение: ~1000 зарегистрированных, в пик 20–50 одновременно активных, ~2500 проверок в месяц.

### Что выдержит без проблем

- **Vercel (фронтенд)** — это просто статический сайт на CDN. 1000 человек для него — ничто. Трогать не нужно.
- **API и база (Railway)** — обычные запросы (вход, история, отчёты) лёгкие и быстрые. При нормальном пуле соединений к базе и паре рабочих процессов спокойно тянут сотни запросов в минуту.

### Что НЕ выдержит — узкие места

1. **Парсинг Avito — главная проблема.** Сейчас все парсинги идут через **один** браузер по очереди, каждый до 90 секунд и съедает ~300–700 МБ памяти. Если 10 человек одновременно жмут «проверить» — десятый ждёт минуты. Это первое, что ляжет.
2. **Счётчик лимитов в памяти** — сломается, как только запустишь вторую копию приложения для масштабирования.
3. **Блокирующие внешние вызовы** (Autocode опрашивается до 40 секунд, ИИ — секунды и деньги) — занимают рабочий процесс.
4. **Память на Railway** — Chromium прожорлив, два параллельных браузера на слабом контейнере = вылет по памяти.

### Что делать (хорошая новость: половина уже заложена в коде)

1. **Вынести парсинг и VIN в фоновые воркеры через очередь** (Redis-очередь уже написана — включить и достроить). API только ставит задачу и сразу отвечает, фронт поллит статус.
2. **Добавить Redis** и перевести на него очередь, лимиты и кэш парсинга (сейчас кэш на диске, а на Railway он эфемерный — теряется при редеплое).
3. **Перейти на внешний скрейпинг-API для Avito** — свой браузер с дата-центрового IP будет тонуть в капче. Это решает самую хрупкую часть. **(Выбран вариант B — см. ниже.)**
4. **Пул соединений к базе** (Supabase pooler / pgbouncer) + индексы на частые запросы.
5. **Sentry + алерты** на долю успешных парсингов и нехватку памяти.

## Часть 6. Выбранный путь — Вариант B (скрейпинг-API) и бюджет

Мы выбрали **Вариант B: внешний скрейпинг-API** (например, ScrapingBee) вместо своего Playwright. Он на пару десятков долларов дороже, но снимает главную головную боль — капчу и вылеты Chromium по памяти, и масштабируется ровнее.

### Что меняется в архитектуре при Варианте B

- Тяжёлый Chromium с Railway **убирается** — браузер держит у себя скрейпинг-сервис.
- Парсер Avito вместо локального Playwright дёргает HTTP-API скрейпера (он возвращает готовый HTML страницы, уже с пройденной защитой и нужными прокси).
- Воркеры на Railway становятся лёгкими (память больше не упирается в браузер).
- Логика разбора HTML (BeautifulSoup) **остаётся как есть** — меняется только слой загрузки.

### Бюджет (Вариант B), при ~2500 проверках в месяц

| Статья | Расчёт | $/мес |
|---|---|---|
| Railway: API + лёгкие воркеры + Postgres + Redis | без тяжёлого Chromium | $35–50 |
| ScrapingBee (тариф Freelance) | 150 000 кредитов; Avito ~25 кредитов/запрос = ~6000 парсингов | $49 |
| OpenRouter (GPT-4o-mini) | ~12М входных + 5М выходных токенов | $5–15 |
| Resend (почта) | бесплатного тарифа хватает | $0 |
| Vercel (фронтенд) | Hobby / Pro | $0–20 |
| **Итого инфраструктура** | | **~$90–135 (≈ 8 000–12 000 ₽)** |

### Считается отдельно (себестоимость, перекладывается на пользователя)

- **Autocode VIN-отчёты** (~750 шт/мес): базовый — от **3 ₽** (~2 250 ₽/мес), полный — от **60 ₽** (~45 000 ₽/мес). Разброс огромный — это закладывается в цену подписки Pro, а не в инфраструктуру.
- **Комиссия ЮKassa** — ~3.5% с оборота.

### Вывод по деньгам

Чистая инфраструктура на 1000 человек — **порядка $90–135 в месяц**. Приятный сюрприз — ИИ почти бесплатен (~$5–15) благодаря дешёвой модели. Главная переменная — глубина Autocode-отчёта: при полных отчётах она легко превысит всю остальную смету, поэтому её нужно заложить в цену Pro.

## Главные риски (помнить всегда)

- **Парсинг Avito** — самая хрупкая точка всей воронки (капча/блокировки). Вариант B её смягчает, но не убирает полностью.
- **Autocode** — платный, при полных отчётах дорогой; нужны лимиты и правильная цена Pro.
- **Два параллельных интерфейса** (Vue SPA и старый Jinja-кабинет) — риск двойной поддержки, лучше свести к одному.
- **Внешние зависимости** (скрейпер, OpenRouter, ЮKassa, Resend) — нужны запасные сценарии на случай их простоя.
