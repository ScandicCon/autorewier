# Командная работа над проектом (Git + GitHub)

**Как вдвоём писать код, проверять друг друга и не ломать `main`.**
Версия 1.0 · июнь 2026

> Репозиторий: `github.com/ScandicCon/autorewier`. CI уже настроен — на каждый PR прогоняются тесты и сборка.

---

## 0. Главное правило

**Никто не пушит напрямую в `main`.** Каждая задача = отдельная ветка → Pull Request (PR) → второй смотрит → CI зелёный → merge. Так вы всегда видите код друг друга и не ломаете рабочую версию.

---

## 1. Базовый цикл работы (GitHub Flow)

```bash
# 1. Перед началом — взять свежий main
git checkout main
git pull

# 2. Создать ветку под задачу
git checkout -b feature/grz-ui      # имя: feature/что-делаешь

# 3. Работать, коммитить маленькими шагами
git add -A
git commit -m "feat: поле ввода гос-номера"

# 4. Отправить ветку на GitHub
git push -u origin feature/grz-ui

# 5. На GitHub открыть Pull Request (кнопка появится сама)
#    → второй ревьюит → CI зелёный → Merge

# 6. После merge — обновить main и удалить ветку
git checkout main
git pull
git branch -d feature/grz-ui
```

**Правила хороших веток/PR:**
- Маленькие PR (одна задача) ревьюятся в разы легче и быстрее мёрджатся.
- Имя ветки понятное: `feature/...`, `fix/...`, `docs/...`.
- Сообщения коммитов осмысленные: `feat: ...`, `fix: ...`, `test: ...`, `docs: ...`.

## 2. Как проверять код, который запушил друг (ревью PR)

1. GitHub → репозиторий → вкладка **Pull requests** → открой его PR.
2. Вкладка **Files changed** — это **diff** (что добавлено/убрано). Читаешь по строкам.
3. Можешь оставить комментарий к конкретной строке (наведи → «+») — вопрос или замечание.
4. Кнопка **Review changes** → выбрать:
   - **Approve** — всё ок, можно мёрджить;
   - **Request changes** — нужно поправить;
   - **Comment** — просто заметки.
5. Перед мёрджем убедись: у PR **зелёная галочка CI** (тесты и сборка прошли).

### Чек-лист ревью (на что смотреть)
- [ ] **CI зелёный** (тесты + сборка прошли).
- [ ] Делает то, что заявлено в названии PR, и не больше.
- [ ] **Нет секретов в коде** (ключи, пароли, токены) — они только в Railway/Vercel/`.env`, не в git.
- [ ] Есть тесты на новую логику (или объяснение, почему нет).
- [ ] Читается, по стилю похоже на остальной код.
- [ ] Не сломаны существующие файлы (CI это поймает, но и глазами полезно).

### Проверить его ветку локально (запустить у себя)
```bash
git fetch                      # подтянуть инфу о ветках
git checkout feature/его-ветка # переключиться на его код
# запустить тесты / поднять локально, посмотреть что работает
git checkout main              # вернуться к себе
```

## 3. Защитить `main` (обязательно для двоих)

Чтобы случайно не запушить сломанное напрямую в main:

GitHub → репозиторий → **Settings** → **Branches** → **Add branch ruleset / rule** для `main`:
- ✅ **Require a pull request before merging** (нельзя пушить в main напрямую).
- ✅ **Require status checks to pass** → выбрать CI-проверки (Backend, Frontend) — без зелёного CI merge заблокирован.
- (опц.) **Require 1 approval** — нужно одобрение второго перед мёрджем.

После этого вся работа физически идёт только через PR + зелёный CI.

---

## 4. Чтобы не мешать друг другу
- **Делите зоны:** один — бэкенд, другой — фронт; или по фичам. Меньше пересечений в одних файлах = меньше конфликтов.
- **Чаще берите свежий `main`** (`git checkout main && git pull`) перед новой веткой.
- **Маленькие частые PR** лучше одного большого — меньше конфликтов и проще ревью.
- **Договоритесь, кто что делает:** заведите простой список задач — вкладка **Issues** на GitHub или общий чат/таблица. Одна задача — один человек — одна ветка.

---

## 5. Если возник конфликт при merge
Это нормально, когда двое правили один файл.
```bash
git checkout main
git pull
git checkout feature/моя-ветка
git merge main            # подтянуть свежий main в свою ветку
# Git покажет конфликтные файлы. Открой, найди <<<<<<< ======= >>>>>>>,
# оставь правильный вариант, убери маркеры.
git add -A
git commit                # завершить merge
git push
```
Если страшно — лучше позвать второго и разрулить вместе, чем затереть чужой код.

## 6. Шпаргалка команд
```bash
git status                 # что изменено сейчас
git pull                   # подтянуть свежее с GitHub
git checkout -b feature/x  # новая ветка
git add -A && git commit -m "..."   # сохранить изменения
git push -u origin feature/x        # отправить ветку
git checkout main          # вернуться на main
git branch                 # список локальных веток
git log --oneline -10      # последние коммиты
```

---

## 7. Что НЕ коммитить
- Секреты: ключи API, пароли, токены, боевые `.env` (для них есть `.gitignore`).
- Большие бинарники/видео без необходимости.
- Сгенерированное (`node_modules`, сборки) — обычно уже в `.gitignore`.

> Если случайно закоммитили секрет — сразу смените этот ключ в провайдере (старый считать скомпрометированным), даже если удалили из репо.
