# Бэкапы базы данных

> Чтобы не потерять пользователей, проверки и платежи при сбое. Два уровня: автоматические бэкапы Railway + свой дамп `pg_dump`.

---

## Уровень 1. Автоматические бэкапы Railway (включить в первую очередь)

1. Railway → твой проект → сервис **Postgres** → вкладка **Backups**.
2. Включи автоматические бэкапы (доступность и частота зависят от тарифа Railway — проверь свой план).
3. Убедись, что задана периодичность (ежедневно) и срок хранения.

Это самый простой уровень защиты — ничего кодить не нужно.

## Уровень 2. Свой дамп `pg_dump` (контроль и переносимость)

В репозитории есть скрипт `scripts/backup_db.sh` — делает сжатый дамп и хранит последние 14 копий.

**Запуск вручную** (в Railway → сервис → вкладка Shell/Console, или локально с прод-URL):

```bash
DATABASE_URL="postgresql://user:pass@host:5432/dbname" bash scripts/backup_db.sh
```

Дамп ляжет в `./backups/autorewier_YYYYMMDD_HHMMSS.sql.gz`. Скрипт сам убирает SQLAlchemy-суффиксы (`+asyncpg`) из URL.

**Автоматизация (по желанию):**
- Через **Railway Cron** — отдельный сервис/задача по расписанию, запускающая скрипт.
- Либо локально по расписанию (Планировщик задач Windows) с прод-`DATABASE_URL`.
- Для надёжности храни копии **вне Railway** (например, заливай в облако/на свой диск) — иначе при потере проекта пропадут и бэкапы.

## Восстановление из дампа

```bash
# создать чистую БД при необходимости, затем:
gunzip -c autorewier_YYYYMMDD_HHMMSS.sql.gz | psql "postgresql://user:pass@host:5432/dbname"
```

## План на случай сбоя (коротко)

1. Поднять новый Postgres (Railway).
2. Прописать новый `DATABASE_URL` в сервис.
3. Восстановить из последнего дампа (команда выше) или из бэкапа Railway.
4. Перезапустить сервис — миграции применятся автоматически (`alembic upgrade head`).

---

**Минимум для запуска:** включить автобэкапы Railway (Уровень 1) и хотя бы раз проверить, что `pg_dump` отрабатывает и дамп восстанавливается. Регулярные внешние копии — добавить после первых платящих пользователей.
