## Карта этапов (в каком порядке делать)

```
Этап 1  Стабилизация + вывод в прод      ← начинаем здесь (без этого сайт не "живой")
Этап 2  Масштаб на 1000–2000 человек     ← чтобы не лёг от запросов
Этап 3  Наблюдаемость: PostHog + Sentry  ← видеть ошибки и поведение
Этап 4  Соц-вход в бою
Этап 5  Пробивка по VIN (Autocode в бою)
Этап 6  Усиление нейросетевого анализа
Этап 7  Пробивка по гос-номеру (Номерограм-стиль)
Этап 8  Тихий запуск → замер экономики
Этап 9  Реклама (только после этапа 8)
Этап 10 Мобильные приложения (App Store / Google Play)
```

Этапы 1–3 — фундамент, делать строго по порядку. Этапы 4–7 можно частично параллелить. Этап 9 (реклама) — **только** после того, как этап 8 подтвердил себестоимость. Этап 10 — после стабильной работы веба.

## ЭТАП 1. Стабилизация и вывод в прод

**Цель:** сайт работает в бою end-to-end. Без этого всё остальное бессмысленно.

### 1.1. Зелёный тест-сьют (фундамент)
- [ ] Прогнать `pytest` целиком, зафиксировать список красных тестов.
- [ ] Починить падающие, добиться зелёного прогона как точки отсчёта.
- [ ] Зафиксировать CI-гейт (`.github/workflows/ci.yml` уже есть — проверить, что он гоняет тесты на PR).
- [ ] Каждую найденную/исправленную ошибку записывать в `docs/ERRORS_LOG.md`.

### 1.2. Боевые переменные в Railway (backend)
Прописать в Railway → Variables (значения — реальные, не из репозитория):
- [ ] `ENVIRONMENT=production`, `STRICT_PRODUCTION_CHECKS=true`
- [ ] `WEB_SECRET_KEY` (64 симв., уже валидный — перенести), `ADMIN_API_TOKEN` (случайная строка)
- [ ] `WEB_BASE_URL=https://<домен>`, `CORS_EXTRA_ORIGINS=https://<vercel-домен>`
- [ ] `WEB_COOKIE_SECURE=true`, `WEB_COOKIE_SAMESITE=none` (Vercel↔Railway — разные домены)
- [ ] `ALLOW_MOCK_SERVICES=false`, `ALLOW_DEV_PAYMENT_BYPASS=false`
- [ ] `DATABASE_URL=postgresql+asyncpg://…` (Postgres, не SQLite)

### 1.3. Frontend в Vercel
- [ ] Root Directory = `frontend/`
- [ ] `VITE_API_URL=https://<railway-домен>`
- [ ] Проверить `vercel.json` (SPA-rewrites, `outputDirectory=dist`) — уже настроен.

### 1.4. Платежи ЮKassa в бою
- [ ] `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_RETURN_URL`, `YOOKASSA_WEBHOOK_ALLOWLIST` в Railway.
- [ ] Тестовый реальный платёж → вебхук → активация Pro → лимит снят.
- [ ] Убедиться, что dev-bypass выключен.

### 1.5. Email-верификация в бою
- [ ] `RESEND_API_KEY` в Railway, подтвердить домен (DKIM/SPF).
- [ ] `REQUIRE_EMAIL_VERIFICATION=true` только после подтверждения домена.

### 1.6. Один фронтенд
- [ ] Решить судьбу двух UI: оставить Vue SPA основным, legacy Jinja свести к лендингу или убрать. Снимает двойную поддержку.

### 1.7. Сквозной smoke-тест на проде
- [ ] Регистрация → письмо верификации дошло → вход.
- [ ] Создать проверку → отчёт с рисками и вердиктом → скачать PDF.
- [ ] Оплатить Pro → вебхук → подписка активна.
- [ ] `/api/v1/health` и `/admin/health` отвечают.

**Готово, когда:** новый пользователь может зарегистрироваться, проверить авто, скачать PDF и оплатить Pro на боевом домене.

## ЭТАП 2. Хостинг на 1000–2000 человек (чтобы не лёг)

**Цель:** сайт держит нагрузку без падений. Полный разбор архитектуры, цифр и расходов — в `docs/guides/HOSTING_COSTS.md`. Здесь — чек-лист действий.

- [ ] **Postgres вместо SQLite** + пул соединений (asyncpg). SQLite не держит конкурентную запись — это первый, кто «ляжет».
- [ ] **Redis** на проде: `REDIS_URL`, `RATE_LIMIT_STORAGE=redis`, `TASK_QUEUE_ENABLED=true`.
- [ ] **Очередь задач**: вынести парсинг/VIN/LLM/PDF в воркер (`python -m app.workers.worker`), поднять его отдельным процессом на Railway. Тяжёлые операции не блокируют веб-ответ.
- [ ] **Кэш в Redis**: результаты парсинга и VIN кэшировать (не платить и не дёргать сайт дважды за одно объявление/VIN).
- [ ] **ScrapingBee вместо своего Chromium**: устойчивость к капче + резко меньше памяти (Chromium прожорлив). После перехода — убрать Playwright из Docker-образа, контейнер станет легче.
- [ ] **Несколько инстансов API** за балансировщиком (Railway масштабирует репликами) — rate limit и сессии уже в Redis, поэтому горизонтальное масштабирование безопасно.
- [ ] **Нагрузочный тест**: прогнать `locust`/`k6` на 60 одновременных пользователей, найти узкие места до рекламы.
- [ ] **Бэкапы БД** (Supabase/Railway авто-бэкапы + `scripts/backup_db.sh`) и план восстановления.

**Готово, когда:** нагрузочный тест на ~60 одновременных проходит без ошибок и роста латентности, тяжёлые задачи идут через воркер.

## ЭТАП 3. Наблюдаемость: PostHog + Sentry

**Цель:** видеть, что делают пользователи (PostHog) и что ломается (Sentry).

### 3.1. PostHog (продуктовая аналитика) — код уже готов
- [ ] Уточнить регион проекта (EU/US) — от этого зависит host.
- [ ] Vercel: `VITE_POSTHOG_KEY=phc_...`, `VITE_POSTHOG_HOST=https://eu.i.posthog.com` → **Redeploy** (Vite вшивает при сборке).
- [ ] Railway: `POSTHOG_API_KEY=phc_...`, `POSTHOG_HOST=https://eu.i.posthog.com`.
- [ ] Проверить, что события доходят (Live events).
- [ ] Настроить главную воронку: регистрация → первая проверка → просмотр отчёта → оплата Pro.
- [ ] Сверить список событий с PRD: `signup`, `email_verified`, `login`, `listing_parse_*`, `inspection_created`, `report_viewed`, `pdf_downloaded`, `vin_check_*`, `subscription_*`, `monitoring_*`.

### 3.2. Sentry (мониторинг ошибок) — код уже готов
- [ ] Создать проект Sentry, получить DSN.
- [ ] Railway: `SENTRY_DSN=...`; Vercel: `VITE_SENTRY_DSN=...` → Redeploy.
- [ ] Привязать к окружению (production) и версии релиза; семплирование трейсов 10–20%.
- [ ] Настроить алерты (email/Telegram) на всплеск ошибок и падение ключевого флоу (парсинг, оплата).
- [ ] Проверить: специально вызвать ошибку → она появилась в Sentry.

**Готово, когда:** в PostHog видна воронка, в Sentry прилетают ошибки с контекстом.

## ЭТАП 4. Соц-вход в бою

**Цель:** кнопки «Войти через…» работают. Код уже реализован (Яндекс, VK, Google, Telegram) — нужны только ключи провайдеров. Подробная инструкция по каждому провайдеру — `docs/deploy/SOCIAL_LOGIN.md`.

- [ ] Общие переменные в Railway: `OAUTH_REDIRECT_BASE=https://<railway-домен>`, при необходимости `OAUTH_SUCCESS_REDIRECT`.
- [ ] **Яндекс ID**: создать приложение на oauth.yandex.ru → `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`.
- [ ] **VK ID**: создать приложение → `VK_CLIENT_ID`, `VK_CLIENT_SECRET`.
- [ ] **Google**: OAuth client ID в Google Cloud → `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`.
- [ ] **Telegram**: `@BotFather` → `/setdomain`; Vercel: `VITE_TELEGRAM_BOT=<username>` → Redeploy.
- [ ] Redirect URI у каждого провайдера: `https://<railway-домен>/api/v1/auth/oauth/<provider>/callback`.
- [ ] Проверить вход каждым провайдером → возврат в кабинет авторизованным.

**Готово, когда:** хотя бы 2–3 провайдера работают; ошибки видны в Sentry.

## ЭТАП 5. Пробивка по VIN (Autocode в бою)

**Цель:** пользователи получают реальную историю авто по VIN, а не демо.

### Как это работает (объяснение)
Сервис `app/services/autocode.py` уже умеет запрашивать отчёт у B2B-API Автокода (`request_vin_report`). Сейчас без ключей работает **демо-режим** (отдаёт заглушку). Как только впишешь реальные ключи → `autocode_enabled = true` → демо выключается, включается **квота**: на Pro 10 базовых отчётов/мес, сверх — платные пакеты (`REPORT_PACKS`: 5/490₽, 10/890₽, 20/1590₽). Это уже встроенная защита от убытка.

Отчёты у Автокода **предоплатные**: списываются с баланса твоего B2B-аккаунта. То есть «куда класть деньги за VIN» = **пополнить баланс в кабинете Автокода для бизнеса**.

### Шаги (подробно — `docs/deploy/AUTOCODE_SETUP.md`)
- [ ] Получить B2B-доступ: avtocod.ru/for-business → способ «Доступ по API». Контакты: b2b@avtocod.ru, +7 (499) 110-49-83. Уточнить, с кем заключают договор (самозанятый/ИП).
- [ ] Уточнить **реальную стоимость** отчётов (базовый/полный) — это прямой драйвер прибыли.
- [ ] Пополнить баланс на тест (10–20 отчётов).
- [ ] Взять ключи: логин, пароль/секрет, домен/endpoint, UID типа отчёта.
- [ ] Railway: `AUTOCODE_USER`, `AUTOCODE_PASSWORD`, `AUTOCODE_DOMAIN`, `AUTOCODE_REPORT_TYPE_UID`.
- [ ] Настроить экономику квоты: правило `включено_в_Pro × себестоимость < 955₽`. Если отчёт дороже ~60₽ — уменьшить `PRO_VIN_REPORTS_INCLUDED` в Railway.
- [ ] Проверить: реальный VIN → настоящий отчёт; превышение квоты → предложение докупить пакет (402).

**Готово, когда:** реальный VIN даёт настоящую историю, квота и докупка работают, баланс списывается корректно.

## ЭТАП 7. Пробивка по гос-номеру (стиль «Номерограм»)

**Цель:** ввод госномера вместо VIN. Это **тонкая надстройка** над готовой VIN-проверкой, не отдельная большая система.

### Как это работает
Госномер сам по себе истории не содержит. Сначала по ГРЗ определяется VIN (Autocode умеет принимать и ГРЗ, либо отдельный сервис ГРЗ→VIN), затем запускается обычный VIN-отчёт из этапа 5.

- [ ] Поле ввода госномера + валидация формата РФ (`А123ВС777`) на веб и в боте.
- [ ] Сервис `grz_lookup`: ГРЗ → VIN через провайдера; кэш в Redis.
- [ ] Та же квота/экономика, что у VIN (платная опция).
- [ ] Мягкая деградация: VIN по номеру не найден → понятное сообщение + ввод VIN вручную.
- [ ] События в PostHog: `grz_lookup_requested`, `grz_lookup_completed`.

**Зависимость:** требует работающего этапа 5 (Autocode в бою). Можно делать сразу после него.
**Примечание:** эту фичу разумно выпустить **после** запуска рекламы — на старте достаточно VIN.

**Готово, когда:** пользователь вводит госномер и получает VIN-отчёт.

- [ ] По PostHog замерить воронку и фактическую конверсию Free→Pro.
- [ ] Замерить фактическую себестоимость одной проверки и долю успешных парсингов (цель >90%).

**Готово, когда:** на живых данных подтверждено, что себестоимость < цены тарифа и парсинг > 90%.

## ЭТАП 10. Мобильные приложения (App Store / Google Play)

**Цель:** нативные приложения после стабильной работы веба.

### Рекомендуемый путь: Capacitor (обёртка существующего Vue SPA)
Минимум усилий, одна кодовая база. Vue SPA оборачивается в нативный контейнер (WebView + нативные плагины: пуши, камера для фото осмотра).

- [ ] Добавить Capacitor в `frontend/`, сконфигурировать iOS и Android проекты.
- [ ] Нативные плагины: камера (фото авто), пуш-уведомления (мониторинг объявлений), deep links (OAuth-возврат).
- [ ] Адаптировать соц-вход и оплату под мобильные правила сторов (важно: Apple/Google берут комиссию 15–30% за продажу цифровых подписок внутри приложения — продумать, оставлять ли оплату Pro вебом или платить комиссию).
- [ ] **Apple App Store**: Apple Developer аккаунт ($99/год), сборка через Xcode/Mac (или облачный билд), прохождение ревью.
- [ ] **Google Play**: аккаунт разработчика ($25 разово), сборка AAB, прохождение ревью.
- [ ] Подготовить листинги: иконки, скриншоты, описание, политика конфиденциальности (URL уже есть).

### Подводные камни
- iOS-сборка требует macOS (Xcode) или облачного CI (например, через GitHub Actions с macOS-раннером).
- Сторы требуют политику конфиденциальности и могут потребовать обоснование сбора данных.
- Оплата цифровых услуг внутри iOS-приложения формально должна идти через Apple IAP — заранее уточнить, не нарушает ли веб-оплата правила (для B2B/SaaS бывают исключения).

**Готово, когда:** приложения опубликованы и проходят базовый сценарий проверки авто.
