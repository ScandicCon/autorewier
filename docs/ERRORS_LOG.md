## Среда разработки (20.06.2026)

### [T-02] Песочница обрезает большие файлы в Linux-зеркале
- **Дата:** 2026-06-20
- **Статус:** ✅ обходится
- **Где:** среда разработки (sandbox), файлы > ~150–280 строк (`app/api/routes.py`, `frontend/src/api/inspectionApi.js`, `frontend/src/views/NewInspectionView.vue`)
- **Симптом:** при записи через файловые инструменты Linux-зеркало получает усечённую копию (обрыв на середине), хотя реальный файл (Windows) целый. Из-за этого `npm run build` / `py_compile` в песочнице падают на «обрезанном» файле.
- **Причина:** нестабильная синхронизация Windows↔Linux для крупных файлов в этой среде. Не дефект кода.
- **Обход:** (1) новый код выносить в небольшие файлы — напр. эндпоинт vision вынесен в `app/api/photo_routes.py` (~80 строк) вместо роста `routes.py`; (2) бэкенд-тесты гонять по файлам (синхронизируются надёжно); (3) фронт-сборку проверять в CI/на Vercel (чистое окружение), а не в песочнице.
- **Профилактика:** не наращивать крупные файлы; держать модули небольшими.

## Результаты прогона тестов (20.06.2026)

### [T-01] Полный pytest-прогон одним процессом виснет в песочнице
- **Дата:** 2026-06-20
- **Статус:** ✅ диагностировано (не баг тестов)
- **Где:** весь сьют (`tests/`), запуск `pytest` одним процессом
- **Симптом:** прогон всех 167 тестов в одном процессе зависает (нон-детерминированно: то на `test_login_sets_cookie`, то на `test_structured_findings_*`); pytest-таймауты (`thread`/`signal`) не прерывают блокирующий вызов.
- **Причина:** загрязнение состояния между тестами + блокирующий сетевой/браузерный вызов, который в песочнице висит (нет fast-fail по сети). **Важно:** при наличии репозиторного `.env` с боевыми ключами зависание сильнее (тесты пытаются ходить во внешние сервисы). В чистом окружении (как в GitHub CI) сьют зелёный.
- **Проверка/решение:** прогнал **каждый тест-файл по отдельности в чистом окружении** (без `.env`, env как в CI) → **все 167 тестов проходят или skip, 0 failed, 0 errors**. Падающих тестов нет.
- **Рекомендация (для надёжного полного прогона везде):**
  - В тестах гарантированно отключать внешние вызовы: `conftest.py` с autouse-фикстурой, которая зануляет `POSTHOG_API_KEY`, `SENTRY_DSN`, `REDIS_URL`, `AUTOCODE_*`, и мокает сетевой слой парсеров/LLM.
  - Не держать боевой `.env` рядом при локальном прогоне (CI его не имеет — поэтому зелёный).
  - Альтернатива для CI-надёжности: `pytest-forked` (каждый тест в своём процессе) убирает загрязнение состояния.
- **Профилактика:** CI уже использует чистое окружение + `--timeout` (`.github/workflows/ci.yml`) — этого достаточно. Локально запускать с временно отключённым `.env`.
- **Сделано (20.06.2026):** добавлен `tests/conftest.py` — autouse-изоляция от внешних сервисов (зануляет PostHog/Sentry/Redis/Autocode/LLM/почту в тест-режиме) + запрет реального запуска Chromium в высокоуровневом парсере Avito. Эффект: полный прогон **с боевым `.env`** на месте дошёл с ~43% (где висло раньше) до ~93% без зависаний. Остаточный «висяк» у самого конца (~93%, ≈12 последних тестов) — **кумулятивное исчерпание ресурсов песочницы** (накопление потоков-порталов `TestClient` за 150+ тестов), не падение: те же файлы отдельной группой дают 25 passed, 4 skipped за 4.2с.
- **Итог:** падающих тестов нет; для гарантированно зелёного полного прогона локально — `pytest-forked` (каждый тест в своём процессе) или шардинг по файлам.
- **Проверка в CI (20.06.2026):** первый прогон GitHub Actions (CI #1, коммит ccceb6a) — **Frontend (build) ✅ прошёл**, **Backend (pytest) ❌ упал** (exit 2 за 29с). Воспроизвёл в чистом клоне репозитория: причина — ровно этот кумулятивный «висяк» при прогоне всех ~165 тестов одним процессом (это был первый CI вообще, зелёным он никогда не был). **Реальных падений нет:** прогон по половинам дал 102 passed + 62 passed, 0 failed; пофайловый прогон — все файлы ok.
- **Фикс (в `.github/workflows/ci.yml`):** шаг тестов переведён на **пофайловый прогон** (свежий процесс на каждый `tests/test_*.py`) с shell-backstop `timeout -s KILL 300`. Это исключает накопление ресурсов за один процесс. `rc=5` (нет неинтеграционных тестов в файле) трактуется как успех.
- **CI #2–#4 всё ещё падали — вторая причина (найдена и исправлена):** GitHub Actions выполняет `run`-блок с `bash -e` (errexit). В пофайловом цикле `pytest` для integration-only файла (`test_playwright_smoke_e2e.py`) возвращает `rc=5` («нет неинтеграционных тестов») — и `-e` прерывал весь шаг ДО ручной проверки `rc`, помечая job красным. Воспроизвёл в чистом клоне: под `bash -e` цикл обрывался на rc=5, не доходя до конца. **Решение:** добавлен `set +e` в начало `run`-блока → коды возврата обрабатываются вручную (`rc≠0 и rc≠5` → fail). Проверено: с `set +e` цикл (включая integration-файл) завершается с кодом 0.

### [R-13] Robokassa: код ошибки 23 «Оплата недоступна» на тестовом платеже
- **Дата:** 2026-06-20
- **Статус:** 🟡 ожидается активация магазина
- **Где:** страница оплаты Robokassa (тест-режим, новый магазин `autorewier`)

- **Профилактика:** не считать 23 ошибкой кода; это состояние магазина у провайдера.

### [R-08] Проверить, что прод в режиме production (не development)
- **Дата:** 2026-06-20
- **Статус:** 🟡 проверяется
- **Где:** переменные Railway (бэкенд)
- **Симптом:** `WEB_SECRET_KEY` задан. `ENVIRONMENT`, `ADMIN_API_TOKEN`, `STRICT_PRODUCTION_CHECKS` НЕ заданы → прод работает как `development`.
- **Оценка риска (после разбора кода):** НИЗКИЙ. `can_use_dev_payment_bypass` и `can_use_mock_services` требуют ещё и `allow_*`-флагов (по умолчанию false, не заданы) → обхода оплаты и демо-моков НЕТ. `web_cookie_secure=true` выставлен явно. Сессии безопасны (ключ есть). Это вопрос гигиены, не дыра.
- **Решение (гигиена, без спешки):** задать `ADMIN_API_TOKEN`, затем `ENVIRONMENT=production` (`STRICT_PRODUCTION_CHECKS` по умолчанию true). После — `/health` должен отвечать; если упал, логи Railway назовут недостающее.
- **Причина:** переменные не прописаны; `is_production=False`, поэтому hardening-проверки не блокируют старт и скрывают проблему.
- **Риск:** сессии/JWT подписываются **публичным дефолтным ключом** — их можно подделать. Админ-API без токена. Прод-hardening выключен.
- **Решение (порядок важен, иначе живой сайт упадёт):**
  1. Сначала задать `WEB_SECRET_KEY` (случайные 48+ симв.) и `ADMIN_API_TOKEN`.
  2. Затем `ENVIRONMENT=production` + `STRICT_PRODUCTION_CHECKS=true`.
  3. Проверить, что сервис поднялся (`/health`), затем сверить `scripts/check_prod_env.py`.
- **Профилактика:** `check_prod_env.py` в Railway перед каждым релизом.

## Открытые / ожидаемые риски (предзаведено из аудита)

Это не баги в коде, а известные точки, где ошибки наиболее вероятны при выводе в прод. Закрывать по `MASTER_PLAN.md`.

### [R-01] Капча/блокировка парсинга Avito
- **Дата:** 2026-06-20
- **Статус:** 🟡 в работе
- **Где:** `app/services/parsers/avito*.py`
- **Симптом:** на новом IP Avito показывает капчу → парсинг падает, воронка рвётся.
- **Причина:** свой Chromium с нового IP детектится антиботом.
- **Решение (план):** переход на ScrapingBee (скрейпинг-API) + мониторинг доли успехов + graceful-фолбэк на ручной ввод.
- **Профилактика:** алерт Sentry на рост доли неуспешных парсингов; контрактный тест на разбор HTML.

### [R-02] Перерасход баланса Autocode
- **Дата:** 2026-06-20
- **Статус:** 🟡 в работе
- **Где:** `app/services/autocode.py`, `app/services/subscription.py`
- **Симптом:** активный перекупщик может «съесть» много полных VIN-отчётов (~60₽/шт) на безлимитной Pro → минус.
- **Причина:** дорогой полный отчёт в безлимитном тарифе.
- **Решение:** квота `PRO_VIN_REPORTS_INCLUDED=10` + платные пакеты `REPORT_PACKS` (уже в коде). Полный отчёт — платная опция.
- **Профилактика:** метрить VIN-запросы по пользователю; сверять `включено × себестоимость < 955₽`.

### [R-03] SQLite не держит конкурентную запись
- **Дата:** 2026-06-20
- **Статус:** 🔴 открыта (закрыть на этапе 2)
- **Где:** `DATABASE_URL` (dev = SQLite)
- **Симптом:** при нескольких одновременных проверках — блокировки БД / ошибки записи.
- **Причина:** SQLite не рассчитан на параллельную запись.
- **Решение (план):** перейти на PostgreSQL (asyncpg) + пул соединений на проде.
- **Профилактика:** нагрузочный тест на 60 одновременных перед рекламой.

### [R-04] Cross-site cookie между Vercel и Railway
- **Дата:** 2026-06-20
- **Статус:** 🔴 открыта (закрыть на этапе 1)
- **Где:** конфиг cookie, CORS
- **Симптом:** при `SameSite=lax` (дефолт) cookie сессии не уходит с Vercel-фронта на Railway-бэкенд → пользователь не залогинен.
- **Причина:** фронт и бэк на разных доменах.
- **Решение:** `WEB_COOKIE_SECURE=true` + `WEB_COOKIE_SAMESITE=none` + `CORS_EXTRA_ORIGINS` с доменом Vercel на проде.
- **Профилактика:** пункт в smoke-тесте деплоя (вход после регистрации).

### [R-05] Production-валидация: 2 жёстких блокера
- **Дата:** 2026-06-20
- **Статус:** 🔴 открыта (закрыть на этапе 1)
- **Где:** production-валидация конфига (`STRICT_PRODUCTION_CHECKS`)
- **Симптом:** при `ENVIRONMENT=production` прод не поднимется: `WEB_BASE_URL` без https и нет `ADMIN_API_TOKEN`.
- **Причина:** dev-значения в конфиге.
- **Решение:** задать `WEB_BASE_URL=https://<домен>` и `ADMIN_API_TOKEN` в Railway.
- **Профилактика:** чек-лист боевых переменных (`MASTER_PLAN.md` §1.2).

### [R-06] Email-верификация без подтверждённого домена
- **Дата:** 2026-06-20
- **Статус:** 🟡 в работе
- **Где:** `app/services/verification_delivery.py`, Resend
- **Симптом:** в проде запрос верификации возвращает 400, если почта не настроена (после фикса — явная ошибка, а не молчание).
- **Причина:** домен Resend не подтверждён (DKIM/SPF).
- **Решение:** подтвердить домен в Resend, затем `REQUIRE_EMAIL_VERIFICATION=true`.
- **Профилактика:** не включать обязательную верификацию до подтверждения домена.
